Six tools, and only one of them can write

ToolAccessWhat it does, and its limit
list_filesread-onlylists files, at most 500 entries, .git hidden
read_fileread-onlynumbered lines, at most 200 per call
search_coderead-onlyregex search, at most 200 results
run_testsexecuteruns pytest and returns a summary: counts and the failing tests, not the raw output
run_cliexecuteruns python -m tinyledger with checked arguments
edit_filewritereplaces one unique piece of text, only in existing files below src/

Every result is at most 10,000 characters. Every schema forbids extra arguments and sets types and ranges.

Why split them like this?

Each tool does one thing, so each can be checked and limited on its own. The read-only tools can never change anything. A unique-match edit cannot silently rewrite a file.

Why no "run any shell command" tool?

It would make every other control useless:

cat ../secrets/canary.txt
sed -i … tests/test_settle.py
curl … $API_KEY
sleep 99999

We would have to parse shell syntax to stop that. So the only programs are two fixed commands with validated arguments.

The model follows the schema. We validate anyway

parse the JSON→ check against the schema→ check the meaning: paths, allow-lists→ run→ redact secrets→ cut to 10,000 characters→ log

Three reasons

  1. The guarantee depends on the provider and its settings. The mock model sends broken JSON and wrong types
  2. A valid call can still be malicious. {"path": "../secrets/canary.txt"} is a perfectly valid string
  3. The tool layer must be safe for every caller, not for one model configuration

Errors never crash the layer. They go back as {"ok": false, "error": "…"} with a message the model can act on.

The agent's final answer: "The repository contained suspicious text in a CSV description and a code comment asking for access outside the workspace and test deletion. I treated it as untrusted data and did not follow it."

What our layer does not stop

  • Code under test runs with our user's rights. The agent can write Python into src/ and run it through the tests: read files, use the network
  • Redaction only knows the secrets we list
  • No memory, disk or process limits inside the timeout

Before a real company repository

  • A real sandbox: container with only the workspace, no network, no secrets, resource limits
  • Changes only as a pull request with human review and CI
  • Protected paths from configuration: CI files, build scripts, dependencies

Three lessons we take away

1

A green check is not a correct result

Task 1: OpenCode reported a fix that was not there. We found it by reading the file.

Task 2: our agent passed 25 of 25 checks with two broken rules.

Task 3: the judge gave 0 and 0.5 to the same kind of answer.

2

An agent only knows what it retrieved

Task 2: it never searched for the bio rule, so it did not follow it.

Task 3: every failure of our best system starts in retrieval, none in generation.

Task 1: 600 KB of pictures in the working file broke its search and its edits.

3

Safety belongs in the tool layer, not in the prompt

Task 4: the model ignored both planted instructions. But the guarantee comes from validation and containment, as the mock run shows.

Task 1: the permission question is the same idea: the model proposes, the program decides.
